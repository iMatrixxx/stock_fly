## 0. 报告思路结构(输出目标形态, 2026-09-17 起受契约约束, 现为 v3)

复盘报告 = **v3 契约骨架(0~10 共十一节 / 30 小节, 含 `### 5.2 中线高潜池`) + 第 3~7 段各自 🔑 一句话总结 + 机读预测卡**。
LLM 撰写时的任务模板见 `assets/llm_report_prompt.md`；但**骨架不再是"提示词里的建议"**——
`report/outline.py` 的 `REPORT_OUTLINE` 是唯一真源，⑧ 门禁的「报告结构」这一路按它校验，
**缺节或乱序直接阻断（不渲染 PDF、不发邮件）**。

**v2 的灵魂是"顺序即因果"**：v1 把资金流放在最前（"半导体流入 136 亿"是**结果**），
读者先拿到结果、再往后找原因；v2 把「1 产业情报」提到最前，先交代"为什么"，再让资金/情绪
去**验证或否证**。因果链因此不可逆：
`产业情报 → 供需推演 → A股映射 → 资金验证 → 情绪验证 → 个股 → 计划`。
v1 无遗留报告（v1 生效日 2026-09-17，当日及以后从未产出 v1 报告），故 v2 **直接替换** v1、
不并行维护——避免两套契约同时存在的漂移；2026-09-16 及更早历史报告按生效日豁免。

| 段 | 小节 | 主要数据来源(evidence 节) | 该段要回答的问题 |
|---|---|---|---|
| 0 摘要与行动卡 | 定调 + 核心结论 + 行动卡表 | 本报告后文(禁止引入新数据) | 只读这一节够不够下单? |
| **1 产业情报** | **1.1 事件与供需推演 / 1.2 A股映射与产业图谱** | `industry_intel`(summary/node_signals/chain_level/stock_watchlist/industry_counts)、**`chain_map`** | **产业侧发生了什么?推演出什么供需变化(涨价/缺货/扩产)?映射到 A 股哪些环节?** |
| 2 数据完整度与口径 | 可用数据源 / 缺口 / 异常 / 假设边界 | `meta.data_sources`、`meta.data_gaps`、`meta.anomalies` | 今天哪些数据可信?哪些结论先天弱? |
| 3 市场环境 | 3.1 指数与成交 / 3.2 情绪温度 / 3.3 四日演变与周期阶段 / 3.4 题材集中度 / **3.5 资金集中度** / 3.6 宏观催化 | `market`(indices/成交/北向)、`emotion`(含 `industry_concentration`)、`cycle_context`、**`capital_concentration`**、`macro` | 今天情绪处于周期哪一段?**钱是摊开的还是压在一处?** |
| 4 资金方向 | 4.1 资金属性 / 4.2 外资与席位 / 4.3 产业观察 / 4.4 资金迁移路径 / 4.5 次日资金预测 | `capital`、`market.northbound`、`dragon_seats`、`dragon_top`、`industry_intel`、`capital_migration`、`capital_forecast`、`board_pools` | 产业事件获资金确认了吗?钱从哪来、到哪去?明天去哪? |
| 5 核心标的 | 5.1 次日高潜池 | `leaders_candidates`、`high_ladder_stocks`、`leader_rivalry` + prompt 尾 `选股候选池` | 谁是龙头?明日取舍哪些标的? |
| 6 交易计划 | 6.1 仓位锁 / 6.2 加仓·降仓触发条件 / 6.3 操作清单 / 6.4 回避清单 | 前五段综合 + `risk_matrix` | 明天具体做什么、什么条件动手? |
| 7 风险矩阵 | 逐行 风险/触发/是否触发/动作 | `risk_matrix` | 什么会打断上述判断? |
| 8 次日预测卡(JSON) | 仅机读 fenced json(≤5 条) | 报告撰写时冻结 → `forecast_<date>.json` | 把可回测判断固化成机读卡 |
| 9 昨日预测验证 | T-1 各卡 实际值/判定 + 命中率 + miss 归因 | prompt 尾 `昨日预测卡验证` 节(scorecard.jsonl 判卷行) | 昨天的判断错在哪?今天要怎么修正? |
| 10 附录 | 数据表 / 公式 / 术语 | evidence 明细(只搬运不新增) | 让人能复核口径与原始表 |

关键设计意图:

1. **"产业情报"前置为第 1 段**(v2 核心改动,原产业观察在 v1 第 3 段):v1 的因果链是
   "看到涨 → 解释涨"——读者先拿到资金流这个**结果**,再往后找原因;v2 把它倒回来,
   先交代产业侧的事件与供需推演(1.1)、再给出环节级映射(1.2),让第 3~4 段的资金/情绪
   去**验证或否证**。判断的来源顺序被写进骨架,而不是靠作者自觉。
2. **"宏观催化"降到 3.6**(原 v1 的 2.5):它本质是"3 市场环境"里的一条价格侧证据
   (期货端是否印证盘面方向),与指数/情绪/题材同层;仍保留"先看价格信号、再谈资金"的
   阅读顺序——读完第 3 段再进第 4 段资金方向。
3. **新增 0 / 2 两段是"可执行性"与"可信度"前置**:0 段让报告能被"只读一节"使用(定调 + 行动卡,
   且动作必须与第 6 段一致);2 段把 `meta.data_gaps` / `anomalies` 从散落脚注提升为独立小节,
   **先说清哪里不可信**,避免读者把"缺口下的推断"当成事实。
4. **新增 9 段把判断闭环写进正文**:M2 判卷账(scorecard)此前只服务于离线校准,作者写报告时
   看不到自己的历史命中率,"报喜不报忧"于是成了默认倾向。现在判卷行由
   `forecast_cards.render_verification_section` 注入 prompt,**落空必须逐条写出来并说明修正**。
5. **结构校验只阻断"缺节/乱序"**:标题层级写错、🔑 条数不足只**告警**——骨架缺失会让读者拿不到
   整块结论(必须拦),而 `###` 还是 `####` 只影响观感,不该让出 PDF 的链路中断。
6. **第 3~7 段以 `**🔑 一句话总结**` 收尾**(2026-09-09 起):报告核心结论不散落长段落,每段只读
   一句即得核心判断。纪律:只提炼本段判断 + 对次日的含义,**≤2 行、禁止引入新数字/新标的/新方向**。
7. **板块必落标的**(2026-09-09 起):任何"板块/主线/方向"判断,凡当日有涨停必须列池内标的
   (名称+连板,1~5 只);查无则明写"当日该板块无涨停、资金在未披露权重股",禁止只给方向不给标的。
8. **题材浓度带数值**:称"主线题材"仅当 `mainline=true`(该题材涨停数/全市场涨停数 ≥20%),
   且必须写出占比数值。
9. **席位结构定资金属性**:龙虎榜资金分析必须区分机构专用/北向/游资营业部结构,不能只列净买 TOP。
10. **新增 3.5 资金集中度**(v2 新增):v1 只有"涨停家数"(通信设备 6 家),对交易意义很弱;
    集中度回答的是"钱是摊开的还是压在一处"。由 `logic/concentration.py` 确定性计算,
    **带板块口径护栏**:Σ板块成交÷两市成交越出 [85%,115%] 即判定板块集合含多层级嵌套,
    `industry` 段整体置 `None`、报告只能引 `zt` 段并原样转写 `industry_absent_reason`。
    分档阈值是初版阈值·待回测校准,`level` 只用于分级表述、不构成买卖建议。
11. **新增 1.2 A股映射与产业图谱**(v2 新增):v1 的方向视图是行业口径(通信设备/半导体/元件),
    而交易上要回答"资金在产业链哪个环节扩散"。由 `logic/chain_map.py` 提供环节级视图,
    盘面标的按 `purity`(core/swing/edge)标受益纯度;**节点级主力净流入无成分级数据,
    禁止把板块级资金流摊到环节上归因**;`totals.zt_coverage_pct` 是映射表完整度、不是收益指标。
12. **两处"标题字面"是硬约束,不是排版偏好**:① `5.1 次日高潜池` 是选股层纪律检查
    (`check_pool_discipline`)的定位锚点,改词会让那一整路检查**静默失效**(它按标题找小节,
    找不到只会报"缺节"或干脆跳过);② 第 8 段标题必须能被「次日预测卡」子串命中,
    否则 `extract_forecast_block` 抽不出卡、`forecast.json` 静默不产(主链只打一行 WARN)。

## 2. 逐轮优化决策记录(2026-09 第 2 周)

> 每轮格式:【反馈/触发】问题原文要点 → 【诊断】根因 → 【方案】选项与拍板 → 【落地】→ 【验证】→ 【教训/局限】。

### R1 板块只写方向、不落个股(09-09)

- **反馈**:报告写"工业金属 +43.18 亿"等板块方向,却没给板块内当日涨停/异动的具体个股
  (哪几只有色涨停?资金在铜还是铝?)。建议补"板块内领涨标的池"。
- **诊断**:evidence 缺"板块 → 当日涨停个股"明细层——涨停股行业标签与板块资金(东财行业板块)
  两套口径并存但从未归组;且当日 72/73 只涨停里**实际无一只真有色股**,工业金属的钱全在
  未涨停大票权重上——"只写方向"恰好掩盖了"该板块当日没有涨停龙头"这一真相。
- **方案(拍板 B:现有池标签归组)**:
  - A 东财成分股抓取(可答铜/铝细分与权重领涨,但需新接口+联调,覆盖到未涨停权重股)
  - **B 现有池标签归组**(涨停/炸板/龙虎榜明细按涨停原因标签归组,改动小、无新抓取)
  - C 先 A 后 B 全量(最完整、工作量最大)
- **落地**:`evidence.py` 新增 `board_pools` 节——`market.zt_pool` 涨停股按行业归组落到个股
  (code/name/ladder/first_seal_time/amount_yi),note 明示口径与"无该行业=当日无涨停、铜/铝
  子板块无成分级数据禁编造";`llm_report_prompt.md` 加"板块必落标的"硬规则 + 自检项;
  test +1(与 zt_total 计数勾稽、降序、字段完整)。
- **验证**:09-08 evidence 离线重建,board_pools 40 行业(农化制品 8/出版 4/化学原料 3/种植业 3…),
  diff 仅新增该节其余零变化;报告第二层补"板块内领涨标的池"段(金正大 2 板封单 12032.14 万列名),
  工业金属按证据诚实落笔——当日无板块内涨停股、外资活跃榜唯一有色权重紫金矿业 26.61 亿。
  verify 478 数字 0 suspects。
- **教训/局限**:未涨停板块权重股名单仍无成分级来源 → 报告只能写"资金在未披露权重股";
  该场景(板块资金流入但无涨停)恰恰是"只给方向"最容易误导之处,今后逢板块必查池、无则明说。

### R2 核心结论分散,建议每层 🔑 一句话总结(09-09)

- **反馈**:报告近 4000 字,核心结论埋在段落里,建议每层末尾提炼核心判断。
- **方案(直接落地)**:`llm_report_prompt.md` 五层结构加"每层收尾纪律"——正文末 `**🔑 一句话总结**`,
  ≤2 行,只提炼本层判断+对次日含义,禁止新数字/新标的(避免🔑 变成第二段正文)。
- **落地**:09-08 报告五层末尾各插一条(如第二层:"资金从科技硬件→工业金属/农化链防御方向,
  但当日该方向无涨停股、承接看权重股;外资仍压注 PCB/光模块——次日科技大概率延续流出,
  周期涨价为唯一共识流入方向")。verify 复跑通过。
- **教训**:提炼纪律必须先于写作 —— prompt 硬要求每层先写正文、🔑 必须能独立成立(脱离上文
  也能读懂),防止写成"见上文"式废句。

### R3 题材集中度无数值、主线无定义(09-09)

- **反馈**:报告说"题材浓度由涨停原因标签近似",却没给具体数值(农化制品占比多少?);
  建议用"该题材涨停数/全市场涨停数"算集中度,>20% 定义为"主线题材"。
- **落地**:`evidence.py` 确定性计算——`emotion.industry_concentration` 每项加
  `ratio_pct`(该题材涨停数/全市场涨停数)+ `mainline`(≥20%);`board_pools.boards[]` 同步加
  `zt_ratio_pct`/`mainline`。note 明示**分母口径差异**:浓度分母=涨停原因标签口径(fuyao
  sealed_total 72),标的池分母=申万行业口径(zt_total 73),两处不可混用。
  prompt:仅 `mainline=true` 可称"主线题材"且必须带占比数值。
- **验证**:09-08 实证——农化制品 11.0%/出版 5.5%/农产品加工 5.5%/化学原料 4.1%/种植业 4.1%,
  **当日无占比达两成的单一主线**,涨停向农业链多子行业分散轮动(直接回答"农化占比多少")。
  test +2 浓度断言;verify 复跑通过。
- **教训**:用户"感觉报告模糊"的通用解药 = 凡是定性说法都问一句"这个能算出来吗、分母是什么"。
  口径(标签 vs 行业)在计算与文档里都须显式,否则数字自相矛盾。

### R4 龙虎榜只列净买 TOP,无买卖席位结构(09-09)

- **反馈**:建议标注"机构专用席位参与情况"——机构净买入则趋势延续强、纯游资偏短线博弈。
- **诊断**:`dragon_top` 是交易所异动披露的**资金聚合事实**,不含买卖前五席位明细;旧报告
  "机构/游资"表述其实是 LLM 从净买数字猜的,无席位依据。
- **方案**:东财席位明细接口探明——`RPT_DAILYBILLBOARD_DETAILSNEW`(榜聚合)→
  `RPT_BILLBOARD_DAILYDETAILSBUY` / `RPT_BILLBOARD_DAILYDETAILSSELL`(每席位一行,
  OPERATEDEPT_NAME 含"机构专用/深股通专用/沪股通专用/营业部")。
- **落地**:新模块 `data/dragon_seats.py`(仿 northbound 零新依赖模式):当日上榜股按净买排序
  取前 12 采样 → 并发拉买卖前五席位 → 席位归三类(**机构专用→org / 深沪股通专用→north /
  营业部→dealer**)→ 聚合 `org_buy_yi/org_sell_yi/org_net_yi` 等。接入 fetch_market 步骤 8
  (try 降级)、`models.MarketData.dragon_seats`、loaders 双向、evidence `dragon_seats` 节、
  prompt 纪律(机构净买=趋势延续信号/净卖=兑现分歧/缺席=纯游资短打;**席位名只来自证据,
  禁止虚构营业部**)。修正一次聚合口径:**席位 NET 是买卖合并净额,机构净额须用席位 NET 汇总,
  不能用卖出榜 SELL 直接减**(卖出榜 SELL 字段语义与席位 NET 不同源)。
- **验证**:09-08 实证——东财榜 55 家、采样净买前 12:机构净买仅上海电影 +1.92 亿(出版/IP,
  买方首位即机构)、中京电子 +0.97、金正大 +0.49 等 5 只;盈新发展/高争民爆机构净卖;
  金健米业等 4 只机构完全缺席;头号买方多为游资营业部(国泰海通武汉紫阳东路 1.34/1.7 亿)。
  → **结论:农业/化肥涨停潮是游资短打,趋势延续性弱于有机构净买的出版/PCB 线**。test +4。
- **教训/局限**:席位数据仅采样净买前 12(全量逐股拉席位 ~59×2 请求过重),`sample_top` 明示
  采样口径;机构净买少 ≠ 板块无机构(可能机构在非上榜股)。

### R5 缺宏观/政策维度,当日无"宏观催化"小节(09-09)

- **反馈**:报告只把"盘后猪肉 4 周连涨、算力规划"当次日素材,但当日盘面为何切向工业金属/农化,
  有无宏观触发(美元/期货夜盘/CPI/PPI 预期)未被纳入;建议加"当日宏观催化"小节。
- **诊断**:evidence 无 macro 字段;报告宏观仅出现在盘后 B 组素材一句。用户实质诉求 =
  "当日切向周期的原因"在数据链上缺位,不是要新闻综述。
- **方案(拍板 A:行情类催化)**:
  - **A 行情类催化(推荐)**:抓宏观矩阵日K(国内商品主连为主),evidence 加 macro 节,报告加
    "当日宏观催化"小节——精确回答"期货/汇率端有无印证盘面切换",可回补 09-08。
  - B 规范+诚实缺省(只改 prompt 加固定小节,改动最小但回补时空泛)

- **数据源实测血泪**(重要教训,写进这里防后人重踩):

### R7 无个股信息源的集成:按"事件粒度"分流,而非强行补 code(09-10)

- **问题**:政策源(miit/ndrc/csrc/cctv,175 条)与电报源(cls/em,976 条)extra 里没有个股
  (`{}` 或 `{policy,org}`),如何接入链路?
- **关键认知(纠偏)**:"没有个股信息"不是缺陷,是**事件粒度的必然**——政策作用于行业、电报是
  线索。实测 175 条政策记录**零条提及上市公司**(全是"十五五规划/答记者问/会议部署")。硬映射
  个股 = 把 `confidence:low` 的行业推断伪装成个股事实,污染 L2 打分与判卷。
- **方案**:`granularity ∈ {stock, node, industry, macro}`,粒度由**信息主体**决定而非信源:
  - `stock` 公告自带 code(零猜测)→ 观察池;电报点名链内标的 → name_match(confidence=low,
    单独计数以便测算精度)
  - `node` 可归位到已建链环节 → 节点信号分;链级政策用 `node=unknown`,不强行塞给单一环节
  - `industry` 行业但未归链(out_of_scope)→ 行业标签 + 报告"宏观催化"
  - `macro` 海外宏观/地缘 → 噪声词典剔除,不入链
  - schema 用 `allOf/if/then` 表达条件必填,只扩三字段(granularity/industry/target),
    chain_id/node 复用
- **两个新词典**:
  - `events/noise_filter.json`:**刻意不收外国公司名**。实测"美光探索近 GPU NAND""SK海力士
    投资""三星泰勒厂产能预定完毕"是产业链**最左侧的领先信号**,剔除即丢失;真正该剔的是
    **海外宏观数据 + 地缘政治 + 海外非中国业务**。`ahook` 白名单(公司名+冒号 / 6 位代码,
    `deny_prefixes` 排除"加拿大总理："类误判)保证 A股公司事件不被误杀;东财公告(extra 有
    code)一律不参与剔除。
  - `events/industry_lexicon.json`:行业词 → `(chain_id, node)` 或行业标签;`node: null` 表示
    链级政策。与 chains 的 `signal_aliases` 分工:别名匹配"涨停原因标签"(短标签),本词典匹配
    "新闻/政策正文"(长句)。
- **接入点分离**:政策源 → 报告第二层"宏观催化"小节 + evidence `industry_intel.policy`;
  电报源 → 节点信号分 → L2 → 报告"产业观察"。**两者不走同一出口**。
- **权重纪律**:policy weight=2 但**半衰期要长**(规划类影响数月),订单/涨价半衰期短(约 3 天);
  用同一衰减系数是错的。
- **实测(全量 8687 条)**:09-08 扫描 2074 → 剔噪 36(全为地缘/海外央行/加拿大关税,**零误杀**)
  → 跨源去重 1 → 候选 30(stock 7 / node 6 / industry 17);真实交易日日均候选 22–40 条,
  量级适合人工二次确认。
- **教训**:
  1. **6 位代码钩子不能用 `\d{6}`**:会误判 8 位日期(20260907),须用 `(?<!\d)\d{6}(?!\d)`。
  2. **标题"公司名+冒号"钩子过宽**:"加拿大总理：…"会被当成公司名逃过过滤,须配
     `deny_prefixes`。
  3. **运营商不是光互连环节**:"电信/5G/6G"归链级,归 optical 会把"政府与运营商签约"误判为
     光模块信号。
  4. **公告源未命中映射表时仍要扫行业词典**:如"子公司中标泰国数据中心项目"正文含"数据中心",
     应归算力链,不能直接落"其他"。
  5. **跨源重复**:同一条电报在 cls 与 em 各出现一次(如受贿案),须按标题去重。
  6. **promote 前的契约校验不要引 jsonschema**:本仓库测试零第三方依赖,自实现
     `validate_event`(必填/枚举/类型/条件必填)即可;且 `entity` 为 null 会违反 schema
     (object 类型),无主体时应整键省略。
  7. **测试勿用 pytest `tmp_path`**:本机沙箱不允许写 `/private/var/folders`,改在
     `tests/_tmp_*` 建临时目录(已 gitignore)。

### R8 次日高潜个股:补上缺失的「判断层」,先回测再上链(09-12)

- **需求**:结构化复盘 harness 如何做架构优化,产出下一个交易日的高潜个股?约定
  **先出方案确认、再开发落地**。
- **问题诊断(不是"加个选股脚本")**:主链 = 数据 → evidence(现象层) → LLM 判断 → 门禁 →
  M2 判卷。**只在现象与校验两端是确定性的,中间的"明日关注谁"完全在 LLM 手里**——个股事实
  散落在 8 个节(`leaders_candidates` / `high_ladder_stocks` / `first_sealer` / `dragon_top` /
  `dragon_seats` / `market.northbound` / `board_pools[].stocks` / `industry_intel.stock_watchlist`),
  却没有任何模块把"明日候选"变成可复现、可判卷的产物。LLM 每次自由选股,既不可复现也无从校准。

- **四个架构决策**:
  1. **判断放代码,取舍留给 LLM**。代码出候选池 → 特征 → 打分 → 排序;LLM 只在池内挑选并写
     失效条件。这是把"能确定性算的绝不交给 LLM 猜"从**算术层延伸到判断层**——打分可回测,
     LLM 的选股不能。
  2. **候选池产物不进 evidence**。evidence 是现象层、打分是判断层,混住破坏纯度(且已 124KB)。
     独立 `outputs/<date>/candidates.json`。**代价:门禁必须升级成双证据源**——这是硬依赖,
     不改则选股段一上链就被自己的门禁拦死(报告的候选分数一律判"证据链外")。
  3. **八源合并 + 角色标签,不设单一入口**。"高潜"在不同情绪阶段不是同一批票:退潮期看回封与
     低位首板、主升期看高标与容量中军。`roles[]` 让下游按阶段取用。
  4. **闭环走独立账本**。`outputs/candidate_scorecard.jsonl` 与 `scorecard.jsonl` 分开——
     后者的样本单元是"报告作者写的一条预测卡",前者是"打分器给出的一个候选",混住会污染
     M2 的命中率校准。

- **落地形态**:新增纯函数包 `stock_review_harness/select/`(`universe` / `features` / `scoring`
  + 版本化权重表 `weights_v{0,1}.json`)与 `tools/backtest_candidates.py`(零联网回测)。
  **刻意先回测后上线**:先证明单因子有信号,再进主链——若 IC 普遍接近 0,此时止损成本最低;
  把没区分度的打分接进报告,等于把噪音固化成"专业结论"。

- **验证(25 个相邻交易日,2026-07-27~09-11,samples 快照离线重建)**:

  | 指标 | v0 先验 | v1 有证据 | v1 样本外 |
  |---|---|---|---|
  | 池基准率 | 18.8% | 19.1% | 20.7% |
  | @K=5 | 36.0% | **60.0%** | 61.7% |
  | tier A | 31.2% | **48.1%** | 47.8% |
  | tier B / C | 19.9 / 14.8 | 17.4 / 12.1 | 18.9 / 14.1 |
  | 分层单调 A≥B≥C | ✓ | ✓ | ✓ |

  A 层 vs 池基准日均差 **+28.97pp,日度 t=9.33,赢 24/25 天**。

- **v1 只做三类改动,全部由 IC 驱动,未做任何权重数值拟合**:
  1. **符号翻转**:`log_amount` / `turnover_rate` / `amount_ratio` → sign=-1
     (IC -0.208 / -0.135 / -0.132,正 IC 天数占比 0% / 20% / 16%,前后半样本同向)。
     含义:**成交额与换手越小,次日越易连板**(惜售效应)。v0 给正号是明显错误。
     最强因子是 `first_seal_min` -0.247(ICIR -2.58)与 `seal_ratio` +0.236(**100% 正 IC 天**)。
  2. **去冗余**:`zt_days`×`zt_count` 秩相关 **1.00**、`amount_ratio`×`turnover_rate` 亦 **1.00**
     → 权重置 0(保留字段供 explain)。两个都计等于把同一因子加权两次。
  3. **下调无区分度组**:`sector` 1.2 → 0.4(组内三特征 IC 均 ≈ -0.02~-0.04)。候选池成员多为
     涨停股,**板块属性在其内部不再区分次日表现**——原设想的"板块共振提升个股次日概率"未被
     证据支持。

- **关键设计:覆盖率向中性收缩**(不是缺失打 0,也不是简单加权平均)。纯加权平均会奖励"信息少的
  票":一只只有资金面一个维度、恰好极高的票会盖过五组都中上但无一项拔尖的票。实测 09-11 不收缩时
  金安国纪凭单组资金 0.88 直接登顶、压过掌握四组的超声电子;收缩后落到第 7。
  `coverage = Σw(可用组)/Σw(全部组)`,`score = [coverage·raw + (1-coverage)·0.5]·100`,
  低于 `min_coverage` 直接不给分。语义:**了解得少,分数就该靠近中性**。

- **教训**:
  1. **先验权重会错在方向上,而且错得静默**。v0 三个量能特征全给正号,看起来合理
     ("成交活跃=关注度高"),实测 25/25 天为负。**没有回测就无法发现这类方向性错误**——
     它不是精度问题,是符号问题。
  2. **调参停在噪音边界**。实测把 `capital` 组权重 1.2→0.4、或 `min_coverage` 0.15→0.35,
     A 层命中率变化都在噪音内(48.1 ↔ 48.8)。**继续调只会过拟合**;正确做法是每日落盘冻结
     候选池让样本自然累积,而不是在同一窗口上反复拟合。
  3. **样本量决定方法上限**。25 个相邻交易日、同日高度相关 → **有效样本 ≈ 25**,只能做单因子
     方向修正,不能做多因子拟合。任何"回测看起来很准"的多因子权重都要先问有效样本量。
  4. **API 保留期决定数据策略**。东财涨停池只保留约 1 个月(实测 08-20 有、08-03 起全为 0)
     → **不能依赖回补**,必须每日冻结;回补只用于冷启动。
  5. **回测必须复用主链的聚合逻辑**。`to_evidence_dict` 是纯函数,离线喂一个
     `DataBundle`(market 来自快照、limit_pool 传空壳)即可重建证据链,`board_pools` /
     `leaders_candidates` 的口径与 live 完全一致——**另写一份回测用的聚合算法必然与生产漂移**。

- **第二期:接进主链(09-12 当日完成)**。四个决策:
  1. **候选池必须先生成、后写报告**。插在主链第 5.6 步(⑦ 报告撰写之前),池子作为证据注入
     prompt。若等报告写完再算池子,LLM 的自由选股就成了既成事实,"在池内取舍"变成事后追认。
     代价是选股段成为 ⑦ 的**前置依赖**,故设计成"失败不阻断复盘"(只告警),不让判断层拖垮现象层。
  2. **门禁升级为双证据源是硬依赖,不是可选项**。`verify_bundle` 原本只吃 `evidence.json`,
     候选分数/覆盖率/派生特征(封单占流通%、首封分钟)都不在链内 → 报告一引用就全被判"编造"而
     阻断。故新增 `candidates.json` 作为并列第二源(经 `source_number_view` 折成数字白名单并入
     数字核对),并**不进 evidence**——现象层与判断层混住会破坏 evidence 纯度。
  3. **选股层纪律的适用范围用"上线日"判,刻意不看 mtime**。候选池文件每次重跑都覆盖,mtime
     立刻比报告新,而"重跑后复查纪律"恰恰最该检查——用 mtime 等于在最需要检查时静默关掉检查。
     改用确定性三元判据:含小节→查;不含且复盘日 < `POOL_FEATURE_FROM`(2026-09-12)→放行(那天
     作者没见过池子,缺节是伪义务);不含且 ≥ 上线日→查(缺节=漏写,阻断)。历史日期补跑因此
     不会被新规则误杀。
  4. **产物分层给,不整份塞 prompt**。`pool` 全量但只带紧凑字段(含**派生特征**——它是报告
     引用 B/C 层个股时唯一的链内依据),`top` 才给全卡(facts/features/score_parts)。`facts`
     不重复带(原始事实全在 evidence)。这样 79 只的全量清单不会把 prompt 撑爆。
  5. **注入是替换式而非追加式**。换权重表重跑不能残留旧分数,否则报告引用的是上一版权重
     算出的数字,而门禁按新产物核对 → 假阳性阻断。
  6. **验收口径**:09-11 端到端 —— 候选池 79 只 / 有分 64(A 10 / B 19 / C 35)、权重 v1、
     环境 expansion;门禁识别 09-11 < 上线日 → 只做数字核对(466 个数字全在链内)+ 覆盖检查
     通过 → 放行 → PDF 产出。**这一轮也验证了"上线日放行"分支确实生效**(而非靠 mtime 侥幸)。

- **第三期:判卷账(09-13 完成)**。七个决策:
  1. **独立账本,不混 `scorecard.jsonl`**。M2 账的样本单元是"报告作者写的一条预测卡",检验**主观
     判断的对错**;候选账的样本单元是"打分器给出的一个候选",检验**排序质量**。混写会直接污染
     M2 的命中率校准——"打分器把某票排第一"与"作者写了一条关于它的预测"是两件事。
  2. **两条护栏必须写成代码,因为它们是"错了不会报错"的类型**。(a) `build_row` 拦住
     `label_date <= candidates_date`:同日自比会把"候选池里本来就有当天已涨停的票"记成命中,
     实测基准率从 **18.75% 抬到 62.5%**——数字好看到没人会怀疑。(b) `monotonic` 在标签无方差
     的一天(池里全中或全落)返回 **None 而非 True**:那时 A≥B≥C 恒成立,算进来只会把单调率抬虚。
     与 `spearman` 遇零方差返回 None 同一原则:**"没有分辨力"与"分层正确"必须分开**。
  3. **无分候选不进排序也不进基准**。它们的"落选"不是排序结果;放进基准分母会人为压低基准率、
     虚增 lift。这是"诚实缺省"在判卷侧的对应条款(打分侧是"缺失不打 0")。
  4. **汇总分 `live` / `backfill` 两块,绝不合并**。回放行是**样本内**的——weights_v1 的三条修正
     正是用同一段 25 日窗口做的,它的分层命中率**不是验证**,只是账本自检。合并成一个"总命中率"
     是最容易犯、也最难被发现的错误。同理 `backfill` 跳过已有真实 `candidates.json` 的日期,
     否则回放会抢占 live 键,而 live 行因幂等被永久跳过。
  5. **幂等键带上权重版本**(`候选日:权重版本`)。同一版本重跑是同一次观测(跳过);换权重表重算
     同一段历史是**另一次合法观测**(正是"新旧权重在同一窗口上对照"要的东西),留在账上分组可查。
  6. **把重复实现上移为包内唯一定义点**。为此新建 `stats.py`(IC 口径)与 `replay.py`(离线回放),
     并把单日读数抽成 `select.ledger.evaluate_pool`,让回测与判卷账**调用同一个函数**。判据是:
     重构后重跑回测,结果与重构前**逐位一致**(除刻意改写的 notes 文案)——可验证的等价,不是"看起来一样"。
     gap 口径同理上移到 `trading_calendar.trading_day_gap`:两处各写一份会让 `clean` 的含义悄悄分叉,
     而"干净样本命中率"正是两个账本的校准依据。
  7. **冷启动靠回放,但立刻标注它是样本内**。结果:25 个相邻交易日(07-30 ~ 09-10)回放读数与
     §13.3 回测逐位一致(A 48.09% / lift 28.97pp / t 9.33 / @K5 60%)。这个"一致"本身就是对
     第 6 条的正向验证——两个独立入口给出同一个数。出 `weights_v2` 的门槛设为 **30 个 live 且
     clean 的天数**,且届时仍只允许单因子方向修正。

### R8 续:方向层——从「股票」升级到「方向」(09-15)

用户原话是"这是你报告最大的缺陷:目前高潜池直接给一批股票,应该先选高潜方向、方向内再选龙头"。
落地时守住了四条:

1. **不另起文件,挂在 `candidates.json` 的 `directions` 段**。方向分与个股分同源同权重版本,必须
   一起冻结、一起可复现;另起文件会制造"方向用了哪天的池子"这种对不上账的问题,也让路径定义扩散。
2. **主口径由覆盖率定,不由偏好定**。实测 `capital_forecast.boards` 只覆盖 8 个方向、与涨停方向
   交集 5 个(≈14%),而 `board_pools` 覆盖全部(36/36)。若以资金为主口径,绝大多数方向会拿不到分。
   故 cluster=1.0 / capital=0.35,资金缺口靠**已有的覆盖率向中性收缩**处理——只有集群证据的方向
   coverage≈0.74,分数向中性靠而**不是被打 0**(打 0 等于断言"这方向最差",而我们只是"没它的数据")。
3. **三个"容易写错"的命名与口径决定**:① 分级名**刻意不用 A/B/C**(报告里 A 层已被个股 tier 占用,
   同一字母指两样东西是最容易写错的那种歧义),改用 一级/二级/观察/**数据不足**,且"数据不足"绝不
   降级成"观察"(观察=看过但不够强,数据不足=不知道);② 星级按**分位数**而非绝对分数切(score 有
   覆盖率上限,coverage=0.74 时满分为 87.0,绝对阈值会把"没资金数据"读成"方向不行");③ 方向特征
   只从 `board_pools` 取(没有涨停的板块不进榜——资金流入但当天无涨停集群属于"资金观察",混进来会让
   方向榜失去与涨停生态的锚)。
4. **打分内核复用而非另写**:方向与个股都走 `scoring.score_rows`,只传不同的特征分组与排序键
   (`board` vs `code`)。排序键显式传参而不是"方向行里也塞个 code 字段兼容"——后者要下游记住
   "方向行的 code 其实是名字",那是会写错的地方。抽取后回测重跑与重构前逐位一致。

**两个实测踩到的坑(已写进测试)**:

- **`sources["board_flows"]` 有两种形状**。evidence 走 `capital_forecast` 时是**列表**,走快照时是
  **字典**;方向层只处理了字典 → 线上直接 `'list' object has no attribute 'items'`,导致**整段选股
  失败、门禁失去第二证据源**(而复盘本身照常完成,警告只是一行 WARN,极易被忽略)。修法:两种形状都
  吃,但**列表形状只认 `main_flow_yi`**——`capital_forecast` 里的 `score` 是规则 impact 求和(0–50
  量纲),拿它当亿元用会让"资金维度"悄悄变成"规则评分维度",这是最不容易被发现的那种口径漂移。
- **`stars` 必须排除出数字白名单**。它是 1~5,进白名单等于放行全部个位数数字,会实质废掉数字核对。
  连带的产品约定:报告写星级要用 `★★★★★` 符号,**不能写「5 星」这种阿拉伯数字**(会被数字核对拦下)。

### R9 报告骨架从"提示词建议"升级为"门禁契约"(09-17)

> **注:本节记录的九段式(v1)契约已于同日被 v2 替换——段号整体顺延(0~9 → 0~10,共 11 节),
> 见 R10。R9 保留原貌作为决策史,文中段号以当时(v1)为准。**

用户给出九段式大纲(0 摘要与行动卡 / 1 数据完整度与口径 / 2 市场环境 / 3 资金方向 / 4 核心标的 /
5 交易计划 / 6 风险矩阵 / 7 次日预测卡 / 8 昨日预测验证 / 9 附录),并要求"固化到 harness 中"。
四个落地决定:

1. **契约是数据,不是文档**。大纲写在 `report/outline.py` 的 `REPORT_OUTLINE`(单一真源),
   提示词、门禁、测试都从它取/对它校验。写进两个地方的规范**必然漂移**——`SELF_CHECKLIST`
   与模板里那份自查清单此前就已经各说各话(11 条 vs 13 条)就是前车之鉴。
2. **按锚点匹配,不按编号匹配**。规范写"2.3 四日演变与周期阶段",但作者可能写"### 四日演变"
   或"#### 2.3 情绪周期阶段"。锚定关键词而非字面编号,避免把排版自由度误判成结构违规。
   代价是每个锚点必须**独占**(不能用"指数""资金"这类跨节短词,否则"某节缺失"永远判不出来)——
   例如 5.1 的锚点刻意不含裸词"仓位"(它是 5.2 标题"加仓/降仓"的子串)。
3. **生效日与选股段同构**。`STRUCTURE_FROM = 2026-09-17`:早于该日的报告是旧骨架,
   要求它符合新契约是伪义务。**历史日重渲染 PDF 必须不被误拦**——这是这条规则存在的全部理由
   (与 `POOL_FEATURE_FROM` 同一套判据哲学;`date_str` 为空则照常检查,不静默放行)。
4. **连带修三处"错了不报错"的地方**(都是这次实测暴露的):
   - `forecast_cards.extract_forecast_block` 原来硬匹配 `## 次日预测卡`,新骨架的标题是
     `## 7. 次日预测卡（JSON）`(`7. ` 插在中间)**直接失配**,症状是 `forecast.json` 静默不产、
     只打一行 WARN → 改为"标题行含关键词"匹配;
   - `_is_benign` 增加**标题编号豁免**:带编号的小节标题会把 `4.1` 这类数字带进报告数字集,
     而它永远不在证据链里 → 每个新骨架报告都会被数字核对拦下一堆"2.1/3.4"。判据是
     "该数字前面只有 `#` 与空格"——正文里的 `2.1 亿` 不受影响;
   - 第 8 段要照抄判卷表的 `target`/`actual`(阈值 17000 之类的历史判断参数),这些数**不在当日
     evidence 里**。不并入白名单,作者为了过门禁只能把命中率写成散文,**正好毁掉这一节的可核查性**
     → `verification_number_view` 折成 `extra_sources` 并入(只取 target/actual,不放 gap/clean 元数据)。

**为什么第 8 段必须由代码喂数据**:预测命中率是这本账唯一的校准信号,靠回忆写必然偏向报喜。
注入 `昨日预测卡验证` 节(判卷行 + 命中率汇总 + "落空不得省略"的纪律)之后,
"如实写"才是一句可执行的话;判卷行缺失时**照样出节**并写"无待验证的预测卡"——
缺节会让作者分不清"今天真没有卡"和"注入挂了"。

### R11 板块口径静默错层:一个"看起来更完整"的降级(09-16)

**症状**:09-16 报告写"电子占两市成交 29.21%",但它与半导体/元件/印制电路板等板块相加远超 100%。

不缺数,只是数字全错。这是 §3.9"两份看起来一样、其实是两套口径"的变体,而且更隐蔽:
连"缺失"都没有,数字还很"丰富"。

1. `data/fetch_market.py` **取消跨层级整组替换**:同花顺口径即使不全也**保留并记 note**,

**方法论**:口径护栏要做成**阈值化的硬判据**(Σ板块成交÷两市成交落区间),而不是靠"板块数量多少"
这类启发式。11 个历史样本实测:扁平口径日全部通过(99~101%),09-16 单独失败(302.2%）——区分度干净。

### R12 事件流二次确认:一个"想当然的自动化"被实测否掉,并暴露公告源噪声豁免的漏洞(09-16)

**症状**:v2 把「1 产业情报」放在因果链起点,但报告第 1 段恒为"当日无已确认产业事件流"。
追查:8 个交易日只有 3 天产出 `events/<date>.jsonl`(09-08/10/11),09-16 明明有 38 条候选躺着
没人确认。**能产、没人产**——预筛没接进主链。

**第一次尝试(错的)**:给预筛加"规则化二次确认",白名单设 `["extra_code"]`,理由是照 docstring
推断"extra_code = 公告源 + 正文自带 code/name + code 已在 chains 映射表内,三项皆机器可判,
二次确认不增加信息量"。**第三条是读代码时想当然出来的**——`classify()` 里 `via=extra_code`
只要求"记录带 code 且 code 未命中行业词典",与是否归链无关(真正判归链要看 `chain_id != "other"`)。
实测三天:extra_code 候选 1/9/15 条,落在 chains 映射表内的 **0 条**;内容多为治理定式
(股东会法律意见书/保荐代表人变更/股东回报规划/工商变更登记),且 `capacity_expansion`
被「**电投产融**」这个公司名命中`投产`、`policy` 被「股东**回报规划**」命中`规划`。
即自动晋级出来的"产业情报"**既不可信也不可用**。

**第二次尝试(对的形状)**:把白名单**默认留空**,机制保留、判断留给配置;报告在事件流为空时
如实写"无已确认产业事件流"而不是编造。同时补上真正拦不住的那一环——见下。

**顺带挖出的结构性漏洞**:`noise_rule()` 对"extra 自带 code"的记录**直接 return None**,即
**公告源整体绕过噪声词典**。原前提是"公告有主体、一定相关",对**产业事件**不成立。故新增
`noise_filter.json` 的 `announcement_noise` 定式词表,并让它**先于 code 豁免**生效

等盘面描述)——它们同样命中信号词,但描述的是"资金在动"而非"产业在变"。

**还修了一个会咬人的 bug**:`promote()` 原先无条件覆盖输出文件。主链每天重跑预筛会把候选池
整体重置为 `confirm=false`,若无脑覆盖,**前几日人工确认攒下的事件会被静默清空**。现改为
"无确认候选时不写文件、保留已有"。

**顺带修掉一个定时炸弹测试**:`tests/test_index_degradation.py` 把日期写死成 `2026-09-11`,
而 `_patch_index_close_from_tencent` 有"距今 ≤5 个自然日"的窗口守卫——09-17 起该测试**必然失败**
(与代码改动无关,纯粹是测试自身写死了绝对日期)。已改为相对今天构造,与同目录的
`test_live_date_guard.py` 对齐。

**方法论**:
1. **`via` 的含义不能靠读 docstring 推断**——它在 `classify()` 的多个分支里被改写
   (`extra_code_lexicon` 就是降级后的 `extra_code`)。白名单的准入条件必须**用实测数字验证**:
   跑三天、打印候选、肉眼判对错,再决定开不开。首版若不上实测就合并,会把治理公告喂进报告开头。
2. **豁免规则也会过期**:code 豁免当年是为"公告必相关"设的,前提变了(开始按标题关键词抽事件),
   豁免就从"防误剔"变成"防正确剔除"。凡是"某类输入跳过全部校验"的设计,都要在引入**新的使用方式**
   时重新审一遍。
3. 目前唯一**可能**安全的一层是 `via=lexicon_node`(经行业词典归位 ⇒ 天然带 chain_id/node)。
   补噪声后实测精度 09-16 为 5/5、09-15 约 7/10。**未默认开启**:第 1 段是 v2 因果链起点,
   用约 70% 精度的规则自动填充它,风险大于"如实写无事件流"。要开就把 `"lexicon_node"`
   填进 `events/signals.json` 的 `auto_confirm_via` 并接受该精度。

### R13 事件确认归属 = 写报告的 LLM:一个"改配置就行"的判断被证伪,确认必须是独立环节(09-17)

**背景**:R12 把预筛接进主链(④.5),候选池每天刷新,但"谁确认"仍未定。`assets/v2_upgrade_mapping.md`
当时的结论是三条路任选,并断言"**预筛与主链集成已完成,无论选哪条都不用再改代码**"(仅 ③ 改一行配置)。

**用户决策(09-17)**:确认归属 = **写报告的 LLM**(它已在环内,第 1 段本就由它撰写,不必新引入角色)。

**那个"不用再改代码"的结论是错的**。`industry_intel` 在 `fetch_market` **步骤 10** 冻结
(读 `events/<date>.jsonl` 聚合),而报告在 ⑦ 才写——**写报告的时点晚于证据链构建**,所以
"让报告 LLM 确认"的产出**永远赶不上当天的证据链**。改配置(开 `auto_confirm_via`)之所以
"不用改代码",是因为它发生在 ④.5 **内部**、必然早于 ⑤;而 LLM 确认发生在环**外**,必须新开环节。
故新增 **④.55 `run_confirm_step`**,夹在 ④.5(刚生成候选池)与 ④.6/⑤ 之间,并配套输出契约
(`confirm_packet.md` 裁定包 → `confirm_decisions.json` 裁定书)。

**教训**:判断"要不要改代码"不能只看**配置面**(有没有开关),要看**时点面**——数据在流水线里
何时物化,晚于该时点的任何判断都进不了当期产物。

**机制:三层防线**(`events/confirm_rules.json` + `logic/event_confirm.py`)
1. **否决规则 veto**(命中即默认不可确认,**可翻案**):澄清/否定、价格反向、关键词只在公司名里、
   治理定式二道防线;
2. **结构性不合格 ineligible**(**不可翻案**):确认了也无处可落——node 粒度但链不在 `chains/`
   索引内(进不了 1.2 产业图谱)、event 级信源产出 stock 粒度且非 `via=name_match`(违反
   "政策/电报源不产个股 target");
3. **LLM 裁定**:只允许 `confirm`/`reject`,**禁止改写 `type/granularity/chain_id/node/target/text`**
   等机器事实字段;归位错了写在 `reason` 里,不改数据。

**纪律落成断言,不落成注释**(承通用规则 8):
- **fail-closed**:裁定书解析容错(容忍常见笔误),但**校验不放宽**——任何一条不合法即**整份不落盘**,
  报错并保持候选池原状,绝不部分生效;
- **上限**:每日 `confirm ≤ 12`(第 1 段是因果链起点,条数过多等于把候选池原样搬进报告开头)、
  **可翻案 ≤ 2** 且翻案须写 `override_reason`(≥4 字);
- **未提及 = 保持未确认**(不默认通过);`reject` 也必须写 `reason`——驳回理由留在候选池里,
  供次日复核规则是否误伤。

**审计字段上移到 schema**:`confirmed_by`/`confirm_reason` 原先只存在于候选池的 `_review`,
而 `promote()` 会**剥掉 `_review`**,导致"这条订单事件是谁确认的、凭什么"在正式事件流里无法回答。
故 `events/schema.json` 升 **v0.3** 增这两个字段,`promote()` 透传(缺省兜底 `human`,
兼容旧的人工打勾路径)。

**幂等与"刻意不做"**:`apply` 可重复执行——候选池每天重建会把 `confirm` 重置为 `false`,
裁定书**独立存放**,重放即可重新打勾。反之,**④.55 刻意不重跑预筛**:重跑会重排 `event_id`,
使刚写好的裁定书全部失效(校验会明确报错,不会静默错配)。

**校准方法论**:规则集**必须用真实候选池验证**,且**宁可漏、不可误伤**——漏掉一条只是少一条情报,
误杀一条会让本该进报告的事件永远进不了,代价不对称。实测:09-14/15/16 三天规则跑通,
**09-16 人工确认集 8/8 全部进入待裁定、零误杀**。首版 `governance_formula_2nd` 曾收"关联交易"
一词,实测会误伤 09-16 的国城矿业(真实的"合作框架协议暨关联交易进展公告"),已收窄。

**跑 09-16 全链时暴露的两个待修**(09-17 18:55 观测,**尚未修**):
1. `counts.tbd` **把"已在正式事件流"的条目也算进待裁定**:09-16 实测 `tbd=25` 而其中 8 条已确认
   → 真正待裁定 **17**;更误导的是 `tbd_chain_bound=5` 里 **5 条全是已确认的**,即
   **真正待裁定且已归链 = 0**。这会让 LLM 把预算花在重复确认上,并误以为有 5 条可用的链上事件。
2. `run_confirm_step` 在裁定书缺失时**无条件**打印"第 1 段将如实写'无已确认产业事件流'",
   而该日事件流实有 8 条 → 提示与实际相反。应改为仅当事件流为空时才这么说。

### R15 资讯链路四跳归约:把"筛选"改成"归约",并补上缺失的第③跳(09-22)

**背景**：链路 `资讯 → 产业事件 → 供需变化 → A股映射` 里,前三跳只有两跳有产物。
09-22 实测漏斗:`2259 条 raw → 326 命中 → 79 候选 → 76 待裁定 → 7 正式事件 → 2.3 KB evidence`。
压缩比看起来漂亮(0.31%),但**成本全压在 LLM 注意力上**：每一条 raw 资讯的**文本**在链路里
被搬了三次(候选池、裁定 packet、prompt 注入),每次都是**标题原文**——条数在变少,每条的信息量
没变,再加上 `text[:100]`/`title[:80]` 这种截断,本质是"砍长度"而不是"做总结"。

**四个泄露点(全部可量化)**：
1. **跨源同题不去重**：命中集里 8 组完全同标题(cls 与 em 搬运同一新闻),注入的 40 条里 3 条是重复对;
2. **同主题不聚合**：一条《轻工纺织产业发展"十五五"规划》在候选池被拆成 4 条(industry×3 + node×1);
3. **噪声淹没信号**：79 条里 `rumor` 23 条、连行业都没归位的 `unmapped` 40 条(51%),
   内含「万达集团在大连成立珩祥置业公司」「非法养老APP诈骗」等与产业链供需无关的条目;
4. **平行通道**：`daily_review._news_brief` 另起一条路往 prompt 注入 40 条原始标题(**跨源不去重、无正文**),
   与事件流互不相识;且它与 `filter_news_signals.collect()` 各自全量 parse 一遍 raw。

**决策**：四跳全部改为**归约(reduction)**而非**筛选(filter)**——每跳的产物是上一跳的
**结构化降维**,而不是"条数变少的同一批文本"。

| 跳 | 产物 | 关键决定 |
|---|---|---|
| ① 读层 | `data/news_raw.py` | **唯一读入口**：日切 + 跨源指纹去重。指纹 = **主体代码 + 归一化标题**。带 code 是刻意的:公告源有大量共用标题模板的记录,只用标题会把不同公司并成一条 |
| ② 产业事件 | `filter_news_signals.reduce_candidates` | 同主题聚合 + **分档预算**。聚合键 = (主体, 粒度, 链, 环节),**刻意不含 `type`** |
| ③ 供需变化 | `logic/supply_demand.py`(**新增**) | 事件 → `{环节, 变量(demand/supply/price/capacity), 方向}` 的**固定规则表**归约 |
| ④ A股映射 | `chain_map.nodes[].sd_variables` | 承接 ③ 的卡,与 `intel_score` **并列不合成** |

**三条被实测/推理逼出来的纪律**：

1. **聚合键不含事件类型**。同一条政策的不同分点会命中不同事件类型(`『印发：鼓励兼并重组』→order_win`、
   `『印发：支持上市融资』→policy`),按 type 分会把一条政策切回多条。**副作用是好的**：
   `industry_intel` 的节点信号分原本会按分点数**重复计分**(一条政策算 4 次),聚合后虚高自然消失。
2. **未锚定档按"事件权重"截断,不按类型硬删**。`unmapped`(无主体、无链、无行业)对 ③ 供需卡
   完全无从贡献,却白占裁定预算;但**不能按类型一刀砍**——「小鹏机器人已完成供应链审厂及核心
   零部件定点」权重 5 且确有价值,却因行业词典未覆盖而落在 `unmapped`。按 `signals.json` 的
   权重降序截断,让权重高的留下、`policy=2` 的沉底,**比按类型删少误伤**。这是"词典覆盖缺口"与
   "噪声"必须区分对待的一个实例。
3. **`subject_key` 两处收窄都是为了防"错并"**。错并会把两条独立事件压成一条,是**静默丢事实**;
   漏并只是多占一点预算——所以宁可漏并。① 主句短于 8 字退回整条标题(`江苏：1—8月投资…`
   的主句只有「江苏」,拿它当键会把当天所有江苏快讯并成一条);② 归一化把 `。` 变成 `.` 后
   **不能一律按句点切**(`成都1宗宅地溢价39.6%成交` 会被切成 `…溢价39`),故句点须**不在数字之间**
   才作分隔符。

**为什么 ③ 跳必须是机器产物而不是 LLM 手写**：报告契约 `Section("1.1", "事件与供需推演")`
早就要求「事件 → 供需变化(涨价/缺货/扩产)的推演链,需标明证据等级」,但 evidence 里没有任何
可核对的供需事实——门禁于是只能核"有没有写",核不了"写得对不对"。补上 `supply_demand` 后,
1.1 的供需推演才有结构化事实可引、门禁才管得住。

**准入纪律是"宁可不产,不产假的"**：`node=unknown` 的链级事件不产卡(归到单一环节就是编造)、
`policy`/`rumor` 显式排除、`low` 置信度不产卡。并加一条**防漂移**：
`EXCLUDED_TYPES` 必须显式列出,`test_variable_table_covers_all_signal_types` 断言
`signals.json` 的每个事件类型都被本层表态(进表或进排除表)——否则词典加了新类型而供需层
默默不认,症状只是"新类型事件永远进不了供需卡、产物上看不出异常"。

**代价**：报告 1.1/1.2 的写法从"自由推演"变成"照卡写方向"。`score` 只用于排序、
**卡只证方向不证幅度**、`verification` 四态措辞原样透传(`not_confirmed ≠ 事件为假`)——
这几条都写进了 `assets/llm_report_prompt.md`。


## 1. 数据链思路(确定性聚合优先,LLM 只做判断不做算术)

```
输入行情/资讯 → data/ 确定性抓取与归一 → 确定性聚合(浓度/溢价/晋级率/席位/宏观对照)
             → evidence_<date>.json(纯数据) → prompt 注入 → LLM 判断与撰写
             → verify 双通道(数字防编造 + 覆盖防漏写) → md2html+Chrome → PDF → SMTP
```

铁律(反复踩坑后确立):

- **能确定性算的,绝不交给 LLM 猜**:题材浓度 ratio_pct、昨日涨停溢价 avg_pct、席位机构净买
  org_net_yi、宏观分组对照,全部由代码算出进 evidence;LLM 只负责"解读与定性"。
- **诚实缺省**:证据链没有的(北向净买额、美元指数、铜/铝子板块成分、未涨停权重股名单)一律
  标注缺失或在 note 明示,报告写"未披露/数据缺失",**禁止用通用知识填补当日事实**。
- **主链自动判卷闭环(M2)**:报告末尾的次日预测卡收盘冻结为 `forecast_<date>.json`,T+1 由
  `score_predictions.py` **纯代码判卷**追加 scorecard.jsonl,na 不计命中率——让预测可回测,
  逼 LLM 写"能被证伪"的判断而非正确废话。

## 3. 通用决策规则(跨轮次沉淀)

1. **用户报"报告缺 X"的默认三步**:① 定位 X 在 evidence 是否有数据 → ② 无数据则探免费可达源
   (先验证历史可回补,再写代码)→ ③ 落"确定性计算 + prompt 纪律 + 测试 + README/schema"四件套,
   并**回补示例日期验证真实产出**,再决定是否重渲染旧 PDF。
2. **能回补的一律回补当日证据**:优化落地后必须离线重建被点名的历史日期(如 09-08),diff 确认
   仅新增、旧数字零变化才覆盖正式 evidence(比较须先 json round-trip 消除 tuple/list 假阳性)。
3. **口径留痕**:两套口径并存处(涨停标签 vs 申万行业、东财 59 vs fuyao 56、成交额 vs 净买额)
   必须在 note 明示,禁止混用;跨源数字落地前做同源交叉验证(沪铜新浪=东财逐位一致)。
4. **诚实缺省 > 看似完整**:没有稳定数据源的维度(美元/外盘)宁可不做、报告写明缺失,也不引入
   会腐烂的抓取或让 LLM 用知识填补当日事实。
5. **同文件编辑必须串行**:两个 Edit 并行发往同一文件曾致函数插入被覆盖丢失(NameError),
   教训:同一文件的多个修改按顺序逐个执行。
6. **新增"判断层"维度时先回测再上链**:凡是要产出"预测/排序/评级"的模块,先落
   **零联网回测 + 单因子 IC + 分层单调性**三件套,证明有信号再接主链。理由:判断层的错误
   是**符号性**的(方向反了),不像数据层那样会报错或缺失;没有回测就只能靠"看起来合理"验收。
7. **权重必须版本化并附证据**:改权重 = 升版本号 + 写 changelog + 记 IC 与验证窗口。
   同一窗口反复调参必须自问有效样本量——**样本不足时,粗糙但有理有据的权重优于精细拟合**。
8. **判卷/评估类代码的护栏要写成断言,不要写成注释**:凡是"算错了不会报错、只会给出好看数字"的
   判据(样本内外不分、标签用了同日、无方差当有信号),一律落成代码护栏并配测试。实测过的三个
   例子:同日自比把基准率从 18.75% 抬到 62.5%;全中/全落的日子被判"分层单调";无分票混进基准
   分母压低基准率。**这类错误的共同点是结果看起来更好**,所以只能靠代码拦。
9. **两份"看起来一样"的实现就是两份会漂移的实现**:同一口径被两处使用时(回测 vs 线上账本、
   M2 gap vs 候选池 gap),把实现上移为唯一定义点,并用"重构前后输出逐位一致"来验证等价,
   而不是靠人眼比对。IC 口径尤其如此——它不一致时表现为"样本不同",而不是报错。
10. **样本内与样本外的读数永不合并**:回放/回测出来的历史读数是**样本内**的,只能用于自检与
   对账;判定有效性只认上线后逐日累积的干净样本。汇总时物理分块(不是加备注),因为备注会被忽略。
11. **适配器型入参必须能吃下调用方可能给的两种形状**:`sources["board_flows"]` 在 evidence 路径下
   是列表、在快照路径下是字典,只处理一种就线上崩(`'list' object has no attribute 'items'`),
   而**这类崩溃的代价被"失败不阻断主链"的设计放大**——复盘照常出、只有一行 WARN,连数字门禁都仍是绿的
   (丢的是第二证据源)。两条推论:① 双形状入参要在适配层一次收干净,别让下游各自判断;
   ② **"不阻断"的降级路径必须有可观测的落点**(产物缺失本身会被门禁发现:无 `candidates.json` =
   无第二证据源),否则降级会静默成为常态。同一函数内的双形状还要额外守住"哪种形状配哪个口径":
   列表形状只认 `main_flow_yi`,不许把 `score`(0–50 量纲)当亿元元用。
12. **跨口径"补数"必须先验能否相加**:当降级/补数路径会引入另一套**层级或口径**的数据时
   (东财 496 嵌套板块 vs 同花顺 90 扁平行业),补进来的数据会让占比类指标**静默失去可比性**
   ——不报错、不缺数,只是数字全错(见 R11)。凡"凑数据"的降级先问一句"它与现有口径能相加吗",
   不能就**保留缺口并记 note**;若该口径已被下游引用,再加一道**阈值化护栏**(如 Σ板块成交÷两市成交
   须落 `[85%,115%]`,越界即整段置 None),让"不可用"变成机器可判的事实,而不是靠人眼发现。
13. **降级链路要"逐环响铃",且回退必须过同一条数据纪律审查**。2026-09-22 出报告时中线池
   `universe` 为 **0**,而门禁五路全绿、PDF 正常发出——根因是**四段静默叠加**:① clist 取数失败被
   降级成"返回空 dict 且不抛异常";② 空 dict 被喂进建池逻辑,主循环空转产出 `0/0` 空壳;
   ③ 门禁见 `scored==0` 判定"这天没有中线段"而跳过;④ 空页还被写进缓存,把故障自锁一个 TTL。
   两条推论:① **降级的每一环都要自己响铃**——只要指望"上游会处理"或"下游会发现",静默就会叠加成
   "看起来正常",而这类错误共同点是**结果看起来更好**(报告不缺节、门禁全绿);
   ② **回退/补数的目标通道必须通过与被替代者相同的纪律审查**——本模块的回退**只允许单向**
   `clist → datacenter`(同日快照不完整时换逐日通道复核),**禁止** `datacenter → clist`,
   因为后者会把"今天"的估值写进历史日,正是本模块第一条纪律禁止的偷未来。**"为拿到数据而回退"
   是回退最常见的误用**——没数据只损失一段结论,拿错数据会污染结论且不留痕迹。
